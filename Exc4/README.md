# Задание 4. Проектирование продажи ОСАГО

### Проработайте реализацию osago-aggregator. Решите:

Суть реализации в том, что при появлении заявки она отправляется в очередь, откуда забирается осаго агрегатором. Он делает все необходимые операции и отправляет результат в очередь. core-app сопоставляет "задачу" и "результат" по ID. С фронта происходит long poll для пользователя, и как только какой то расчет посчитался, ему сразу выдается результат.

1. Требуется ли ему своё хранилище данных?
    - Нет, используется очередь

2. Какой API он предоставляет core-app?
    - Никакой, они общаются через очередь

3. Определите средство интеграции между сервисами core-app и osago-aggregator.
    - Kafka

4. Подумайте над API для веб-приложения в core-app.
    - Получение результатов расчета ОСАГО, чтобы получать их в реальном вресени можно использтовать Long Poll с фронта до бэка
    - Оформление страховки
    
5. Определите средство интеграции между веб-приложением и core-app. Если будете использовать средство, отличное от REST, отразите интеграцию новой стрелкой.
    - Будет REST

6. В зависимости от выбранных средств интеграции подумайте, требуется ли где-то применение паттернов отказоустойчивости:
   - Rate Limiting - можно для ограничения запросов со стороны пользователей для защиты от DDOS и многих задач на запросы к API ,
   - Circuit Breaker - в часть, где происходит запрос к API страховой компании,
   - Retry - в часть, где происходит запрос к API страховой компании,
   - Timeout - в часть, где происходит запрос к API страховой компании и Long Poll с фронта.

8. Примите во внимание, что сервисы задеплоены в нескольких экземплярах. Подумайте, зависит ли ваше решение от этого.
    - Нет, сервисы stateless
