# Задание 3. Переход на Event-Driven архитектуру

### Проанализируйте текущую архитектуру, напишите список проблем и рисков

1. Основная проблема – на core-app заключено очень много функциональности, и его отказ означает падение всей системы. Идеальным вариантом является распил сервиса на микросервисы - сервис получения тарифов, сервис оформления заявок, сервис предоставления данных об оформленных заявках. Так как это сложно и долго, есть другой способ - сделать сервис stateless и провести горизонтальное масштабирование.
2. Получение информации по продуктам и тарифам происходит со стороны core раз в 15 минут, и сервис ins-product-aggregator начинает синхронно обращаться к каждой стразовой компании по API. Это плохо, потому что ошибки в API могут повлиять на запрос, сделать его медленее (особенно при увеличении числа страховых компаний). Кроме того, тарифы за 15 минут могут стать неактуальными. Решение — сервис ins-product-aggregator должен сампериодически ходить в API и обновлять базу products-db, которая будет расположена перед core. Core прост о будет асинхронно забирать оттуда актуальные тарифы, а ins-product-aggregator будет асинхронно их добавлять.
3. Также можно создать очередь, куда core будет отсылать события при оформлении страховки. Тогда ins-comp-settlement не нужно ходить в core, а нужно будет просто вытаскивать сообщения из очереди тогда, когда ему нужно. Это уменьшает  связаность между сервисами и повышает стабильность.
4. Transactional Outbox в дданном контексте использоваться пока не будет.
